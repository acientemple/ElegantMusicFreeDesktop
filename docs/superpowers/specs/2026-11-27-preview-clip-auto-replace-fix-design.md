# 自动换完整版失效的排查与修复

日期：2026-11-27
状态：已实现并验证

## 现象

用户反馈：「有些音乐还是播放不完整版，没有自动播放完整版。」

即：播到 30 秒左右就断了，应用没有自动换成完整版继续播。

## 排查

### 先确认哪些歌真的只是片段

对歌单里的歌逐个取音源、读 HTTP 头的 `Content-Length`（128kbps ≈ 16KB/s），
反推真实音频长度，跟条目上声明的时长对比：

| 平台 | 声明 | 实际 | 样本 |
| --- | --- | --- | --- |
| 热门歌单 | 312s | **30s** | You Were My Everything |
| 热门歌单 | 235s | **30s** | 童年 - 罗大佑 |
| 热门歌单 | 210s | **30s** | 你的样子 - 罗大佑 |
| 热门歌单 | 316s | **30s** | 恋曲1990 - 罗大佑 |
| 酷狗音乐 | 271s | **68s** | Golden (Live) |
| 完整版搜索 / QQ音乐 | — | 与声明一致 | 正常 |

主流平台给的条目上写的是**完整歌曲的时长**，实际音频只有 30 秒 —— 光看声明时长发现不了。

### 根因一：一次慢插件把整次检索作废（主因）

`findFullVersion`（`src/renderer/core/music-full-version/index.ts`）原来是这么检索的：

```ts
const settled = await Promise.race([
    Promise.allSettled(requests),      // 所有插件一起等
    delay(SEARCH_TIMEOUT).then(() => null),   // 整体 8 秒兜底
]);
if (!settled) {
    return null;      // ← 整体超时 → 整次检索作废
}
```

**8 秒是给所有插件的总额，不是每个插件的。** 只要有一个插件慢，整次检索就白做了。

实测各插件 `getMusicAlternatives` 的耗时：

| 歌曲 | full-track | kugou | qq-music | 结果 |
| --- | --- | --- | --- | --- |
| You Were My Everything | 2506ms | 1329ms | **13462ms** | 整体超时 → 放弃 |
| 童年 | 1743ms | 1015ms | **7551ms** | 整体超时 → 放弃 |
| 你的样子 | 1707ms | 1317ms | 3817ms | 正常 |

QQ音乐插件要连着发好几轮检索，慢的时候十几秒。它一慢，
`full-track`、`kugou` 已经搜到的结果就全被丢掉了 —— 这就是「**有些**歌不自动换」的原因：
快的时候正常，慢的时候就失效。

手动「搜索完整播放版本」弹窗早就修过这个问题（每个插件单独 8 秒兜底），
自动这条链路漏改了。

### 根因二：片段判定只看「绝对秒数」，漏掉长歌被截短

判定只认「实测 ≤ 60 秒」。酷狗那条 `Golden (Live)` 声明 271 秒、实际只有 68 秒 ——
68 > 60，直接漏掉，永远不会触发检索。

### 根因三：短歌会白等 8 秒

声明时长 ≤ 60 秒的歌（儿歌、影视片段）会被当成片段，播放前先做一次完整版检索，
**播放被阻塞最多 8 秒**，而结果几乎必然是「没有完整版」。

## 修复

### 1. 每个插件单独兜底（核心）

`findFullVersion` 改成跟手动弹窗一致：每个插件各自 8 秒，超时的按「没搜到」处理，
不影响其它插件的结果。超时标记为 `PLUGIN_SEARCH_TIMEOUT`，弹窗也改成用这个共享常量。

### 2. 检索不完整时不记「已查过」

`searchedKeys` 记录的是「查过了，确实没有完整版」。只要有插件超时（或全部报错），
这次检索就不算查完，**不写** `searchedKeys` —— 下次播放还会再试，
不会因为一次运气不好就把这首歌永久拉黑。

### 3. 片段判定加「比例」判据

`isPreviewItem` 改成三条判据：

- **实测与声明一致**（差 ≤ 2 秒）→ 歌曲本来就短，是完整的，不是片段；
- **声明或实测 ≤ 60 秒** → 片段（用户给的判据：一分钟之内）；
- **声明 ≥ 120 秒 且 实测 ≤ 声明 × 0.6** → 长歌被截短（覆盖 68 秒这类）。

`declared ≥ 120 秒` 的门槛是为了不误伤儿歌这类本来就短的歌。

`checkPreviewClip` 的入口条件也跟着改：原来只看「实测 ≤ 60 秒」，
现在用 `isPreviewItem(声明, 实测)`，否则 68 秒的片段连检索都进不去。

### 4. 播放前不再阻塞检索

`playIndex` 里原来 `await findFullVersion(...)` —— 检索要几秒，播放就被卡住几秒。
改成只查**缓存**（之前已经找到过的完整版，命中就立即换上，不等网络）；
没命中就先把歌唱起来，交给「实测 → 判定 → 检索 → 替换」这条链路处理。

### 5. 元数据一到位就量时长

片段长度以前只靠 `ontimeupdate`（播放中才触发）才能测到。
改成 `loadedmetadata` 时就把时长报上去，开播瞬间就能判定是不是片段；
另外补了 `durationchange` —— HLS 音源的时长要等缓冲得差不多才从 Infinity 变成真实值，
那一刻正是判断「拿到的到底是不是 30 秒试听」的关键。

### 6. 候选排序：原唱里挑时长最接近原曲的

实机验证时发现另一个问题：换是换成了，但选出来的是《童年 (DJ Candy版)》(6:29)，
而不是录音室版《童年》(3:53)。

`pickFullVersion` 原来的排序是「原唱优先 → 取时长长的」。同一首歌的 DJ 版、
混音版、现场版都比原曲长，按「取最长的」挑，选中的往往是混音版。

改成「原唱优先 → **时长最接近原曲声明时长**的优先 → 都差不多才取长的」。
原曲声明的时长就是这首歌本身的长度（条目上写的是完整歌曲的时长），
最接近它的那个才是同一首歌的正常版本。

只有声明的时长 ≥ 120 秒（像个正常歌曲长度）时才这么比 —— 声明 30 秒的那种是
「平台把片段长度写成了歌曲长度」，比不了接近度。

实测候选（罗大佑《童年》，声明 235 秒）：

| 排序 | 选中的 |
| --- | --- |
| 旧规则（取最长） | 酷狗音乐 389s《童年 (DJ Candy版)》 |
| 新规则（取最接近） | QQ音乐 233s《童年 - 罗大佑》✅ |

## 取舍

- **自动链路的单插件超时仍是 8 秒**：跟手动弹窗一致（两处现在共用同一个常量）。
  慢插件的结果会被丢掉，但通常有别的插件兜底；真要等更久，用户会先手动搜。
- **「实测 = 声明」判为完整**：代价是「平台把片段的时长就写成 30 秒」这种情况会漏掉。
  实际观察到的主流平台都是把完整歌曲的时长写在条目上，所以这个代价可以接受。
- **比例判据可能误判**：声明 300 秒、实际 100 秒的正常歌会被当成片段去检索一次，
  检索不到就什么都不变。代价是一次多余的网络请求。
- **播放前不再阻塞检索**：代价是已知的片段要多播一秒才会被换掉，
  换来的是短歌（儿歌）不再白等 8 秒。

## 验证

- `npx tsc --noEmit` 通过；`npm test` 全绿（68 个用例，新增片段判定与逐插件超时的单测）。
- Node 沙箱实测：三个插件并发检索，最慢的 qq-music 超过 8 秒时，
  full-track / kugou 的结果不再被丢弃。
- 实机验证（打包版 + CDP 观察）：在「中文经典」里播放声明 03:55、实际 00:30 的
  《童年 - 罗大佑》，10 秒内弹出「已自动换成完整版」，播放源换成
  **QQ音乐 03:53 的正片**（不是 DJ 混音版），歌单里的条目同步被升级。
- 数据复查：musicStore 2329 条、3820 个歌单引用，**无悬空引用**。
